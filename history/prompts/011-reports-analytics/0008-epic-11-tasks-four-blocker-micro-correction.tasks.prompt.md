## Prompt

A 22-section governing correction brief titled "Epic 11 — Reports & Analytics: Final `tasks.md` Micro-Correction Pass — 4 Blocking Issues Only" was provided, deliberately scoped narrow: fix exactly four remaining blocking inconsistencies in the already-structurally-corrected `tasks.md`, without redesigning architecture, reopening settled decisions, or renumbering the entire task graph unless strictly necessary. The four blockers, in full:

**Blocker A — Registry consistency vs. composite reports**: `T032`'s registry-consistency test asserted every `status==NOW` report must have an entry in `ADAPTER_REGISTRY`. That's correct for the six operational domains but wrong for `exec.dashboard`/`crossmodule.customer_360`, which are intentionally implemented by `ExecutiveDashboardService`/`Customer360Service`, not `ReportAdapter`-driven dispatch. Required fix: add a typed `ReportExecutionKind` (`ADAPTER | COMPOSITE`) to `ReportDefinition`, and make the registry-consistency test branch structurally on it — `ADAPTER` entries need an `ADAPTER_REGISTRY` entry; `COMPOSITE` entries need a registered handler in a new `COMPOSITE_REPORT_HANDLERS` mapping that resolves to the exact same callable its dedicated route (`GET /reports/dashboard`/`GET /reports/customer-360/{id}`) actually uses — never a hardcoded "if dashboard/customer360: skip" exception, and never forcing the generic `GET /reports/{report_key}` route to execute composite reports (Customer 360's required `customer_id` makes that inappropriate).

**Blocker B — Accounting AR/AP export still full-fetch**: `accounting.ar_aging`/`accounting.ap_aging` were classified Category B (bounded by customer/supplier cardinality) — not a safe technical bound, since a large tenant may have 100,000+ customers/suppliers, and the plan must not load the full population merely to discover it's too large. Required fix: inspect the authoritative AR/AP services/repositories; add a narrowly-scoped, additive, Accounting-owned bounded read/count seam (`count_ar_aging_rows`/`get_ar_aging_page` and AP equivalents) preserving the exact existing aging calculation semantics, SQL-level count/retrieval, additive-only, backward-compatibility-regression-tested; reclassify both as Category A for both online pagination and export.

**Blocker C — Purchase `supplier_performance` full-fetch**: still fetches all suppliers and slices in Python; "supplier cardinality" was likewise rejected as not a guaranteed bound, and calling this "separate debt" is unacceptable when Epic 11's own contract depends on it. Required fix: extend the existing Purchase source-domain seam task with a Purchase-owned bounded implementation (`count_supplier_performance`/genuine SQL-level `.limit()/.offset()`), preserving the existing KPI/business calculation, aggregation remaining Purchase-owned, Reports never importing Purchase repositories directly; reclassify as Category A. After this and Blocker B, Category B should contain only a case with a real enforced hard cap (Installments `due_overdue`/`aging` via `_DUE_STATE_POPULATION_BOUND=50_000`) — re-verified, not assumed. A full re-audit of every export category was required afterward, plus propagating the fix to *online* pagination too (not export-only) — page 1 must not require a full-population fetch either, once the bounded seams exist — and updating the Expected File Map, since it can no longer claim only four existing files are modified.

**Blocker D — Saved View update/PATCH lifecycle inconsistency**: the task graph implemented `create/list/load/delete` but not `update`/`PATCH`, yet the audit task already required `create/update/delete` audit rows — an internal inconsistency. Required fix: re-check the approved `spec.md`/`plan.md` (not infer) for whether update is required; if so, implement it properly end-to-end (repository/service/API/audit/frontend/tests with the full adversarial matrix — owner can update, non-owner/cross-tenant cannot, soft-deleted rows can't be updated, invalid filters rejected, audit exactly once); if not, remove every update claim consistently. Additional, related micro-fixes bundled into this same blocker: (9) the frontend API-client task's awkward "add `loadSavedView` once T140 is live — it is, by Phase 7" prose should just list the final exact method set directly, since by Phase 7 every dependency is already satisfied; (10) restore/identify a dedicated, executable Saved View ownership security test — not a Gate ID standing in for one; (11) audit the final security regression task and remove any reference to a Gate ID cited as though it were a security test; (12–14) recheck and correct Phase 7's stated dependency graph — if its API client defines `getDashboard()`/`getCustomer360()`/`exportReport()` against real contracts, Phase 7 cannot truthfully claim independence from Phases 4/5/6, and `ExportButton` must not be treated as independent of the export backend; the preferred resolution is a corrected dependency statement (`Phase 3 → Phase 4+5 → Phase 6 → Phase 7`), not renumbering, since the phases are already numbered in that order.
