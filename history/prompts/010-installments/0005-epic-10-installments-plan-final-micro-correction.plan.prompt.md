### Correction 1 — Remove All Remaining `FAILED` Idempotency-State References

The corrected §20 Idempotency Strategy correctly removed `FAILED` from the persistent idempotency lifecycle. However, at least one stale reference remains elsewhere in the plan, including the Domain Model summary, which still describes `IN_PROGRESS → COMPLETED|FAILED`. Final decision: persisted `InstallmentIdempotencyKey.status` values are only `IN_PROGRESS`/`COMPLETED`; no persisted `FAILED`. Search the entire `plan.md` and synchronized planning artifacts for `FAILED`, `COMPLETED|FAILED`, `IN_PROGRESS → COMPLETED|FAILED`, and idempotency failure-state wording; update every stale reference so data-model description, schema, ADR-INST-08, testing, failure/recovery, and API semantics all describe the same two-state persisted lifecycle.

### Correction 2 — Simplify Concurrent Idempotency Semantics

The corrected plan documents PostgreSQL blocking behavior correctly (B blocks until A commits or rolls back) but should not present ordinary `IN_PROGRESS → 409 "request already in progress"` as a primary expected outcome, since B only ever observes a *resolved* (committed or rolled-back) state of A, never a genuinely visible in-progress row from another session. Final decision: normal two-request concurrency has exactly two outcomes (A commits → B replays or 409s on payload mismatch; A rolls back → B acquires the reservation and executes normally). The design may defensively retain code for an unexpected visible `IN_PROGRESS` row if useful, but must document it as defensive/unexpected, not the normal contract, and must not advertise `409 request already in progress` as a normal expected response. Update §20.2, §20.3, §22, API error semantics, idempotency tests, ADR-INST-08. Testing must explicitly prove: (1) concurrent same-key/same-payload → one execution, second waits, replays after commit; (2) concurrent same-key/different-payload → one execution, second waits, 409 after commit; (3) first request rolls back → second becomes owner, key not stranded. No test should depend on seeing an uncommitted `IN_PROGRESS` row from another session.

### Correction 3 — Contract Completion Must Include Outstanding Late-Charge AR

The original collection lifecycle treated `schedule outstanding == 0` as sufficient for completion. After the corrected late-charge architecture this is insufficient — a contract may have zero scheduled outstanding but a positive late-charge `DEBIT_NOTE` AR outstanding, which must block `COMPLETED` per the approved invariant that a contract cannot complete while an authoritative outstanding obligation remains. Final completion rule: `complete()` may transition only when all authoritative obligations (scheduled obligation via Accounting payments, and any linked late-charge `ARTransaction` that remains open/outstanding) are satisfied or validly waived/reversed/written off. Recommended architecture: a single authoritative completion check (e.g. `InstallmentOutstandingService.assert_zero_outstanding(contract_id)`) reconciling schedule state and linked late-charge AR via authoritative Accounting reads — not `sum(schedule_line outstanding) == 0` alone. Apply to all completion paths: ordinary collection, early settlement, `DEFAULTED → COMPLETED`, any internal `complete()`, contract detail balance calculation, reporting, success criteria/testing. Required tests: Test A (all scheduled lines paid, one late-charge AR remains open → contract stays ACTIVE/DEFAULTED); Test B (scheduled + late-charge AR both fully paid → may complete); Test C (scheduled paid + late charge validly waived/reversed → may complete); Test D (concurrent last-installment payment + late-charge state mutation cannot produce premature completion).

### Correction 4 — Freeze Accounting Extension Commit Ownership

The corrected plan proposes extending `adjust_receivable()` and adding `reverse_adjustment()` so late-charge Accounting truth is consistent, but the broader Installments workflow must remain one atomic transaction including Accounting GL rows, `ARTransaction`, ledger recompute, `InstallmentLateCharge`, Installments audit, and outbox/event metadata — requiring an explicit commit-ownership contract. Final architectural requirement: when Accounting service methods are invoked from Installments as part of a larger cross-module workflow, they MUST support caller-owned transaction mode — they must NOT commit before Installments has staged its own related rows. Re-inspect the actual behavior of `PostingEngine.stage_direct_posting()`/`finalize_and_publish()`/`reverse()`, `PaymentService`, `AccountsReceivableService`, and any method that currently commits internally, then plan the smallest safe extension — do not merely say "use stage_direct_posting()/finalize_and_publish()" if `finalize_and_publish()` itself commits before Installments rows are staged; the plan must explicitly identify who owns the final commit. Choose one repository-consistent design: Pattern A (staged Accounting API returning identifiers, Installments calls the final commit), Pattern B (existing `commit=False`/caller-owned unit-of-work parameter, if one already exists), or Pattern C (refactor existing public method internals so standalone calls still commit as before while a cross-module staged variant shares internal logic without committing) — do not create duplicate financial logic. A method that commits GL/AR first and lets Installments insert metadata later does NOT satisfy Epic 10's atomicity requirement; the plan must make this impossible by architecture, not convention. Update Repository Findings, §12, §21, §22, §31, Phase 6, Risks/Trade-Offs, ADR-INST-01 if needed, and any Accounting integration contract in research.md/data-model.md. Required integration test: force a failure after Accounting rows are staged but before `InstallmentLateCharge`/audit completes — expected result: `JournalEntry` absent, `ARTransaction` absent, `CustomerLedger` unchanged, `InstallmentLateCharge` absent, `InstallmentAuditLog` absent, outbox event absent. No partial commit acceptable.
