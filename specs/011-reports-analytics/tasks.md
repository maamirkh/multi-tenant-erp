2. **Phase 1 saved-view `load()` depended on Phase 3's execution service**, yet Phase 1's gate treated it as passable anyway. **Fixed**: Phase 1 now implements only `save()` (self-contained — validated against a **test-fixture** registry entry, not real Phase 2 data) and `delete()`/list/create; the public `GET /saved-views/{id}` endpoint and its full re-validation logic move entirely to Phase 3, after `_authorize_and_validate()` exists. Phase 1's gate now requires zero incomplete tasks.
3. **Installments execution-integration tasks lived in Phase 2** despite depending on Phase 3's execution service (the continuity-gate wiring into `_authorize_and_validate()`, the Case A/B HTTP-level test, the metadata-flag test). **Fixed**: moved to Phase 3. Phase 2's Installments sub-phase now contains only the adapter, the continuity-gate *service* itself (a pure, independently-testable unit), its allow-list unit test, registry entries, and adapter-level (non-HTTP) tests.
4. **Every domain's "equivalence"/"reconciliation" test in Phase 2 called the not-yet-existing Epic 11 HTTP endpoint** (`GET /reports/accounting.trial_balance`, etc.) and the GL cursor-continuity test paginated through `GET /reports/accounting.gl`. **Fixed**: Phase 2 equivalence tests now compare the **authoritative domain service's own output directly against the adapter's `run()` output** (no HTTP layer at all). HTTP-level cross-checks against the Epic 11 endpoint, and the GL online-cursor-continuity test, move to Phase 3 (after the endpoint exists).
5. **`execute()` was defined before `ADAPTER_REGISTRY`**, a genuine forward dependency. **Fixed**: `ADAPTER_REGISTRY` construction now precedes `execute()` in Phase 3's task order.
6. **Registry count claimed "45 NOW + 3 DEFERRED" at the end of Phase 2**, but `exec.dashboard`/`crossmodule.customer_360` (2 of the 45) are not implemented until Phases 4/5. **Fixed**: Phase 2 ends at **43 NOW + 3 DEFERRED**; `exec.dashboard` is registered only in Phase 4 (→44), `crossmodule.customer_360` only in Phase 5 (→45). No `NOW`-status placeholder for either exists before its real implementation lands — a `NOW` registry entry is only ever created once its `authoritative_source` genuinely resolves and its endpoint genuinely exists.
7. **Export-boundedness incorrectly conflated a date-range filter with a row-count bound** for several Purchase/Inventory/Accounting reports. **Fixed**: every exportable report is now classified into exactly one of four categories (A: cheap SQL-level count exists; B: no count, but the result is structurally capped by a real business dimension, e.g. customer/supplier count — not by an unbounded date range; C: genuinely unbounded — receives a new, additive, small source-domain pagination/count seam; D: aggregate/fixed-shape, no row concept). This required three **new, narrowly-scoped, additive source-domain tasks** (Purchase, Inventory, Accounting), which changes the "only four files modified" claim — corrected throughout.
8. **Dashboard `WidgetState` was defined as `PRESENT | OMITTED` in one task and silently mutated to add `UNAVAILABLE` in a later task.** **Fixed**: `WidgetState = PRESENT | OMITTED | UNAVAILABLE` is defined once, in the schema task, with a single, non-contradictory partial-failure rule: a widget becomes `UNAVAILABLE` **only** when the adapter raises the specific, typed `UnavailablePrerequisiteError` (a known, expected condition); every other, genuinely unexpected exception propagates as a 5xx and is never silently converted into a widget state.
9. **Dashboard widget count was inconsistent** (schema listed 8, prose implied 9). **Fixed**: recounted directly from spec FR-RPT-040's comma-separated list — **10** distinct widgets (Net Sales, Gross Sales, Purchase Spend, AR balance, AP balance, Cash Position, Operational Inventory Value, CRM Pipeline+Win Rate, Installment Principal+Overdue, Recognized Gross Profit Margin — AR and AP are separate widgets, not combined). Used consistently in schema, composition, tests, frontend, and the coverage matrix.
10. **Customer 360's section-evaluation task referenced the Executive Dashboard service** as an adapter-access path, creating an accidental Phase 5→Phase 4 dependency. **Fixed**: Customer 360 now calls the six domain adapters directly via `ADAPTER_REGISTRY` (Phase 2), never through `ExecutiveDashboardService` — Dashboard and Customer 360 remain independent, parallelizable phases after Phase 3, as the plan intended.
11. **Migration-generation task assumed `074` would import the mutable `REPORTS_PERMISSIONS` Python tuple at migration-run time.** Repository inspection of `071_installments_permission_backfill.py` confirmed the actual, deliberate project convention is the opposite: migrations contain **literal hardcoded SQL** with zero application-code imports (explicitly documented in `071`'s own docstring). **Fixed**: `074` now hardcodes the 16 permission codes/labels as local literals, mirroring `071` exactly; a new consistency test asserts the migration's literal codes exactly match `REPORTS_PERMISSIONS` (guarding drift at test time, not migration-run time).
12. **`SavedReportView.filter_config` was typed `Mapped[dict[str, Any]]`**, an unexamined `Any` usage. **Fixed**: replaced with a proper recursive `JsonValue` type alias, documented as legitimate JSONB-persistence typing (distinct from, and not an exception to, the "no `Any` across Reports execution/public contracts" rule, which governs adapter/service/schema boundaries, not raw JSON column storage).
